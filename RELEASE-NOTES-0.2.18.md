# Seylo 0.2.18

Update from Settings > Updates: the panel updates first, then each node. Nothing to run on the servers. New installs: `curl -fsSL https://install.seylo.dev | sudo sh`.

What's new in full: https://docs.seylo.dev/self-hosting/whats-new-in-0-2-18

## New

- **Alerts say which project.** With many projects that each have an "api" or a "web", an alert titled "api crashed" did not say which one. Every alert about a service now starts with its project: "acme-shop / api crashed", and for a member of a compose stack, its stack too: "acme-shop / shop / shop-web crashed". This covers crashes and the crash limit ("acme-shop / api was stopped after 3 crashes"), deploys that failed or went out, failed builds, health checks, failed backups (and backups that never reported back), cron jobs, uptime checks and certificates. Some titles are worded differently to fit: "Deploy of api failed" is now "acme-shop / api failed to deploy", "Build of api failed" is "acme-shop / api failed to build", "Backup of db failed" is "acme-shop / db: backup failed", "Cron job weekly on worker failed" is "acme-shop / worker: cron job weekly failed" (or "timed out"), an uptime check's "Homepage is down" is "acme-shop / web: Homepage is down" (and "is up again"), and "No certificate for shop.example.com" is "acme-shop / web: no certificate for shop.example.com". Node, panel and security alerts keep their titles. A title is written when the alert is raised: renaming a project or service later leaves the alerts already raised as they were, and the next alert uses the new name.
- **Notifications name the project and service.** Every channel gets them, by their current names, for an alert about a service. The webhook JSON adds `projectName`, `stackName` (a compose member's stack), `serviceName` and `serviceUrl` (the service's page), each null when the alert is not about one; the fields it had stay the same. Discord embeds and Slack messages get Project, Stack and Service fields, with the service linked to its page; Telegram and email get the same as lines ("Project: acme-shop", "Service: api"). ntfy, Pushover, Gotify and Web Push open the service's page when the alert has no link of its own, as a failed cron job has none (before, they opened nothing, or the dashboard). In the API and MCP: `alerts.list` adds `projectName`, `serviceName` and `stackName` (current names), and `serviceProjectId`, the project the service is in now.

## Improved

- **The Templates toolbar.** The status line under the Templates title is gone. The owner's **Catalog source** button and a refresh icon button (**Check for new templates**, for people with templates.manage) now sit left of the search on the title row; on a phone the search takes its own row under them. The refresh button spins while it checks and ends with the same toasts as before. When something is wrong (a failed check or a bad signature, a private catalog that failed, downloads of the official catalog switched off, a build without the catalog's key) the button gets an amber dot, and its tooltip says what is wrong and what to do; while all is well there is no dot and no line. The Catalog source dialog now says what is in use: where the catalog comes from, when it was built, its commit (linked to the Templates repo for the official catalog), the last check, and the problems, the same for a private catalog. Templates that need a newer panel or could not be read keep a short note under the title, only when there are any.
- **New templates show up without a click.** Opening the Templates page asks the panel for a check in the background when the last one is more than 10 minutes old, for anyone signed in, and never starts a second while one runs (scheduled, manual or another page's). A newer catalog then appears on the open page by itself. The check is the panel's own, like the one every 6 hours, so it is not in the activity log; **Check for new templates** still is. In the API: `templates.checkCatalogIfDue` (a GET, read-only keys may call it) and `templates.catalogStatus`'s `checkDue`.
- **An unchanged catalog costs one small request.** Each check sends `If-None-Match` and `If-Modified-Since` for the downloaded catalog in use, official or private, so when nothing changed the server answers 304 (for the official catalog, GitHub's file host does) and the signature is not downloaded again. A private catalog's server that sends neither header gets a full request every time, as before.
- **The dashboard's Alerts card opens the service.** The title of an alert about a service links to the service's page, in the project the service is in now.

## Fixed

- **Links of alerts about a service moved to another project went to its old project.** An alert keeps the project it was raised in, and its link was stored with it, so after a move `alerts.list`'s `link` (in the API and MCP), and a notification or push sent after the move, pointed at `/p/<old project>/s/<service>`. Links to the service's pages now follow it to its current project; other links stay as they were.

## After the update

- Nothing to run by hand: no migration, and everything in 0.2.18 is in the panel. The nodes need nothing new.
- The new alert titles may break filters on the old wording: email rules, Slack or Discord keyword alerts, or scripts that match "Deploy of", "Build of", "Backup of", "Cron job", "No certificate for" or a title that starts with the service's name. Match on the webhook's `event` and `serviceId` (or the new `projectName` and `serviceName`) instead of the title. Alerts raised before the update keep their old titles.
- Webhook receivers get four new fields (`projectName`, `stackName`, `serviceName`, `serviceUrl`). `projectId` stays the project the alert was raised in; `serviceUrl`, and `link` when it is one of the service's pages, point where the service is now.
- What the line under the Templates title said is now in the refresh button's tooltip (when something is wrong) and the Catalog source dialog. People without templates.manage see the search alone on the title row.
