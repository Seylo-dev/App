# Seylo 0.2.11

Update from Settings > Updates: the panel updates first, then each node. Nothing to run on the servers. New installs: `curl -fsSL https://install.seylo.dev | sudo sh`.

What's new in full: https://docs.seylo.dev/self-hosting/whats-new-in-0-2-11

## New

- **Run any image of a database's engine.** A database can run any tag or digest of its engine's own image, like creating any other Docker app: `mongo:8.2.12`, `mongo:8.2`, `mongo:latest`, an old release or a digest, and `postgres` (or `pgvector/pgvector`), `mysql`, `mariadb`, `redis`, `valkey/valkey`, `clickhouse/clickhouse-server`, `eqalpha/keydb` and `ghcr.io/dragonflydb/dragonfly` alike. On the Version card, "Use another image" takes it, starting from the image that runs; the New database form has "Use another image" under Version, starting from the picked version's image. Images of other repositories are still refused: Seylo's settings for a database (its environment, data folder, health check and command) are made for its engine's image. A change the Version card used to refuse now says what can go wrong and goes ahead once you tick "I understand": an older version than what runs (newer data files may not open on it), a Postgres major (it does not open another major's files in place), a skipped version, a version outside Seylo's catalog (not tested by Seylo), a floating tag (what it points at can change on the next deploy), a digest, or another Postgres base system (text indexes may need `REINDEX`). The backup step stays for every change but a newer patch, and a new version that never gets healthy brings the old container back on the same data. For PostgreSQL, whose images from 18 on keep their data in another folder than older ones, Seylo sets `PGDATA` in the database's variables before such a move (and when a database is made from a tag that names no release, such as `postgres:latest`), so a version that cannot read the data fails and the old container comes back, instead of starting on an empty database. MongoDB's compatibility step runs only for a one-step upgrade between Seylo's versions; for other MongoDB moves the card says MongoDB may refuse data whose compatibility version it does not support. The database shows the version its tag names ("MongoDB 8.2"), or the image when the tag names none ("MongoDB (mongo:latest)"). Exported with its data and imported on another panel, it keeps the image it ran whenever that panel's own image of the version could read the data differently (a newer release, a floating tag, a digest, another Postgres base system). A move to a MySQL image from 8.4 on that Seylo does not offer, such as `mysql:9.1.0`, or to a tag that names no release, first gets the `mysql_native_password` account check described under Fixed; MySQL 9 removed that sign-in method, so there the only way out is switching the accounts. The image that runs is still "nothing to change", but for turning MySQL 8.4's old logins on or off. In the API and MCP: `databases.create` takes `image`; `databases.setVersion` takes any `image` (its `version` is then not needed) and `acceptRisk`, and refuses without it with reason `riskNotAccepted` (`details.risk`, `details.risks`, `details.message`); `databases.versionChoices` says `risk` and `risks` for each version, `anyImage`, `repository` and `release`. A rollback to a deployment of another image is still refused.

## Improved

- **Every version change Seylo makes without a risk ran on the real images.** MySQL 8.0 to 8.4, MariaDB 11.4 to 11.8, Redis 7.4 to 8.2, Valkey 8.1 to 9.0 to 9.1 (and 8.1 straight to 9.1), ClickHouse 26.3 to 26.8 and a PostgreSQL 17 patch update (the pinned 17.6 to 17.11) now run in Seylo's test setup the way a node runs them, on the same data with the same settings, and every one kept the data, like MongoDB 7.0 to 8.0 to 9.0 and MariaDB 10.11 to 11.4 since 0.2.9. Some of the risks above ran there too: a MongoDB 8.0 database moved to `mongo:8.2.12`, a version outside the catalog, kept its data; a MongoDB 9.0 database set to the 8.0 image, and a PostgreSQL 18 database set to 17 (with `PGDATA` set) or a 17 one set to 18, never got healthy and came back on the version they ran, with their data. Exposing a MongoDB 9.0 database over TLS ran there too.
- **MongoDB 9.0.8 and 8.0.38.** New MongoDB 9.0 and 8.0 databases start on these newest patch releases, and existing ones can take them as a patch update on the Version card (no backup needed). The upgrade from 7.0 to 8.0 to 9.0, backups, the web UI and TLS ran on them in Seylo's test setup. MongoDB 7.0 stays on 7.0.45: Docker Hub's `mongo:7.0.48` had no Linux image when this release was made.
- **A clearer message for a tag of another version.** A release of another version, such as `mongo:8.2.12` on a MongoDB 8.0 database, used to be refused as "not an exact MongoDB 8.0 release". It is now a move to that version (see any image above), and what can go wrong says which version the tag is and that Seylo does not offer it, so the change is not tested by Seylo (8.2 was MongoDB's short-lived rapid release, which no longer gets fixes). A moving tag such as `mongo:8.2` or `latest` says that it is not an exact release and moves to each new release.

## Fixed

- Changing a MySQL database from 8.0 to 8.4 could lock out some of its logins. MySQL 8.4 turns the old `mysql_native_password` sign-in method off, so accounts made with it (common for older apps and users made by hand) could no longer sign in, while the data was fine. Before that change the panel now checks the running database for such accounts. If it finds any, nothing changes and the Version card names them, with two ways out: switch them to `caching_sha2_password` (`ALTER USER ... IDENTIFIED WITH caching_sha2_password BY '...'`, which needs each account's password), or tick "Keep mysql_native_password logins working in 8.4", which starts 8.4 with `--mysql-native-password=ON`. Later deploys, clones and 8.4 updates keep that, and the Version card shows "Old mysql_native_password logins are on". The check signs in as MySQL's root user, so it works for databases whose admin user is not root too, also right after a password reset, before the next deploy. A MySQL 8.4 database can also turn those logins on or off without changing its image: the Version card has a "Keep old mysql_native_password logins working" switch with Apply, which restarts the database on the image it runs, also a tag such as `mysql:8.4`, with nothing to accept and no backup step (turning them off checks for such accounts first, as above). An import keeps the option when the exported MySQL 8.4 ran with it, so its old logins keep working after the move; nothing else of the file's command comes along. In the API and MCP: `databases.setVersion` refuses with reason `nativePasswordUsers` (or `nativePasswordCheckFailed` when the check cannot run) and takes `keepNativePassword`, also alone on the image the database runs; `databases.versionChoices` says `nativePassword`.
- Resetting the password of a MySQL or MariaDB database whose admin user is not root left root on the old password, while the database's container got the new one as `MYSQL_ROOT_PASSWORD` (`MARIADB_ROOT_PASSWORD`) on its next deploy, so signing in as root with it failed (ERROR 1045), and so did the panel's own steps that sign in as root, such as the next password reset and the MySQL 8.4 check above. A reset now gives root the new password too. A database an older reset already left that way still takes a reset: the admin's password changes, and the new password dialog says that root kept its older password and how to set it (`databases.resetPassword` returns it as `warning`). Once root has that password, later resets keep both in step.
- The API and MCP listed a database's deployments from before a version change as ones it could roll back to (`canRollback`), while the rollback itself refuses them (reason `databaseVersion`), since an older version may not read the files a newer one changed. `deployments.list` and `deployments.get` now say `canRollback: false` for a database's deployment of another image than the one it runs.
