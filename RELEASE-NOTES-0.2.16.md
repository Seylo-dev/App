# Seylo 0.2.16

Update from Settings > Updates: the panel updates first, then each node. Nothing to run on the servers. New installs: `curl -fsSL https://install.seylo.dev | sudo sh`.

What's new in full: https://docs.seylo.dev/self-hosting/whats-new-in-0-2-16

## New

- **Right-click menus.** Right-click a service, project or node, or a row on the Deployments, Domains, Backups, Cron jobs, Alerts, database Users or assistant chats screens, or any table row with a "..." menu, to get the same menu its "..." button has. On a touch screen a long-press opens it; from the keyboard, Shift+F10 or the context menu key. A service's menu (the header's "..." and its right-click menu in the sidebar, the dashboard's Cards, List and Table views and the project page) has Open, Open in new tab, Deploy, Cancel deploy or Restart, Stop and Start, Logs, Console, Clone, Move to project, Move to another node, Copy address, Copy ID and Delete; Stop and Delete ask first, as the header and the Settings tab do. A project's menu has Open, Open in new tab, New service, Rename, Collapse or Expand (for the view it was opened in), Hide project, Settings, Copy ID and Delete (once the project has no services). Each row under Nodes gets a "..." too, with the node's views, Run health checks, Update now and its addresses to copy. The browser's own menu stays on text fields, the code editors, terminals, logs, code and copy fields, selected text, and anywhere with Shift+right-click; on a touch screen, a long-press on those keeps the browser's text selection.
- **Timed expose for databases.** A database's Connection tab has a Timed expose card. It opens the database's port to your IP (or the IPs you type) for 15 minutes to 24 hours, 1 hour by default, and shows the address, the connection URL (with the password only for people who can see the credentials) and a ready `psql`, `mysql`, `mariadb`, `mongosh`, `redis-cli` or `clickhouse-client` command that asks for the password at the prompt, so it never lands in your shell history. ClickHouse can open its HTTP port 8123 too. A timed expose adds no TLS: the card says when the database's own TLS applies (MySQL, MariaDB 11.4 and later, a Postgres while it is exposed) and otherwise says plainly that the connection is not encrypted. Only the allowed IPs get through, and the node closes it on time even with the panel down. Before, timed exposes were only offered on the Domains tab, which databases do not have. In the API and MCP: `exposures.openTimed`'s `targetPort` is optional (a database's port, else the service's main port) and a database takes only its own port (ClickHouse: 9000 or 8123); a database's timed exposes carry `database` (client command and URL without the password), and `databases.connection` lists their URLs with the password (`timed`).
- **Exposed databases can accept connections without TLS.** The Exposed connection card on a database's Connection tab has **Allow connections without TLS**, off by default. Turned on, the node passes clients that do not ask for TLS to the database instead of refusing them, for Postgres, MySQL, MariaDB, MongoDB, Redis, Valkey, KeyDB, Dragonfly and ClickHouse; TLS clients connect as before, the allowed IPs still apply and the connection URL keeps asking for TLS. It asks you to confirm first, because queries, data and, with some sign-in methods, the password travel unencrypted (for the Redis-like engines and ClickHouse, the password itself), in stronger words while the port is open to every IP; emptying the allowed IPs later while it is on asks again. Turning it off refuses new plain clients at once and closes the plain sessions that are open, without touching TLS ones. It is in the activity log, and it needs the node's agent 0.2.16: until then the switch says so and the port stays TLS only. MySQL clients without TLS need the server's public key to send the password (`mysql --ssl-mode=DISABLED --get-server-public-key`, or `allowPublicKeyRetrieval=true` in JDBC). In the API and MCP: `databases.setExposure` takes `allowPlain`; `databases.get` returns `exposure.allowPlain` and `exposure.plainNeedsNodeUpdate`, and `databases.connection` returns `exposed.allowPlain`. An AI working through the MCP or the assistant waits for a person's approval before it lets clients in without TLS, or widens the allowed IPs while they are allowed (emptying the list, or adding any address it does not cover); the Approvals page and the assistant's card show such a request with a Without TLS chip and what it allows and from where, and Approve asks first in red. A request the panel would refuse anyway (an agent too old, MariaDB 10.11, a bad allowed IP, a port in use) is refused at once instead of waiting for an approval that would fail. Its other exposure changes run right away, and MCP tokens skip the approval while Ask before destructive actions is off. Saving allowed IPs that let every IP in (`0.0.0.0/0`, `::/0`, or ranges that add up to every address) while plain connections are allowed asks you to confirm, like an empty list. In the API and MCP, pending approvals carry `warning`.
- **`DOMAINS`: every domain of a service in one reference.** Apps, compose members and Boxes now have `${{api.DOMAINS}}` next to `DOMAIN`. It lists every host the service answers on, comma separated with no spaces: the primary domain first, then the others in the order the Domains tab lists them (`api.example.com,www.example.com`). Redirect-only domains are left out, a host with several paths counts once, and it is empty while the service has no domain. `${{api.DOMAINS[1]}}` picks one domain, counting from 0, so `DOMAINS[0]` is the primary domain, the same host as `DOMAIN`; it works inside longer values too (`https://${{api.DOMAINS[1]}}/v1`). The Environment editor treats both like any reference: completions offer `DOMAINS[0]`, `DOMAINS[1]`, ... with their hosts when the service has several, the hover shows the host, and the References panel has a `DOMAINS` chip. An index past the last domain gets an amber warning that says how many the service has ("api has 2 domains: DOMAINS[0] and DOMAINS[1]") and stays empty until it has that many; an index on another variable, such as `${{api.URL[1]}}`, is a red error; a broken index (`DOMAINS[-1]`, `DOMAINS[ 1 ]`, `DOMAINS[]`) blocks the save. A value that spells out a service's domains (`ALLOWED_HOSTS=api.example.com,www.example.com`) gets the hint to use `${{api.DOMAINS}}`, and one that spells out its second domain `${{api.DOMAINS[1]}}`. As with `DOMAIN`, a domain change shows in the References panel right away and reaches running containers on their next deploy. In the API and MCP: `env.references` marks the variable `list: true`, and `env.set`, `env.setVariable` and `env.analyze` return two new diagnostics, `not-a-list` (error) and `index-out-of-range` (warning).
- **Choose what a database backup holds, and see it.** A database's backup schedule backs up Everything on this server (as before: all databases, for PostgreSQL the users and roles too) or Chosen databases, picked from a live list with their sizes. With one database chosen it can take only some of its tables (PostgreSQL, MySQL, MariaDB) or collections (MongoDB); Redis, Valkey, KeyDB, Dragonfly and ClickHouse still back up everything. Each backup shows its databases as chips with their size, plus the compressed file size and how long it took, and the arrow opens its tables with their size and approximate rows; backups made before 0.2.16, or by older nodes, show "Everything on this server" and the total. A chosen database or table that no longer exists is skipped with a warning on the run, and when nothing is left the backup fails and says why. Restoring a backup of chosen databases replaces only those databases, tables or collections and leaves everything else, users included, as it is; the restore dialog names them, and "Back up the current data first" backs up the same selection (and goes ahead when there is nothing left to keep). A PostgreSQL table that another table references cannot be restored alone: the restore fails and changes nothing. Several PostgreSQL or MongoDB databases in one backup are one object (`.bundle`), so Keep newest, signing and delete work as before. MySQL 5.7 images are listed too. Choosing databases needs 0.2.16 nodes (the dialog says "Update <node>"); older nodes keep backing up and restoring everything. In the API and MCP: `backups.listDatabases` and `backups.runContents`; `backups.createPolicy` and `backups.updatePolicy` take `selection`, and runs carry `scope`, `contents` and `warnings`.
- **Advanced tab for databases: move a database to another node.** A database's page has an Advanced tab (and Move to another node in its menu) with Move to another node, resource limits (Save and restart applies them, offline for a few seconds) and the crash policy. Before a move, the card says what happens on the node you pick: the database stops while its data is copied (with its size at the last backup), it starts there with the same data, users and passwords, its internal address stays the same (and the card names services on other nodes that lose it, since nodes share no private network), its exposed port and timed exposes move to the new node's address with the same allowed IPs and TLS settings, the services reading its `EXPOSED_*` variables need a deploy (listed), and backup schedules carry on there, with Back up now first. Nodes that cannot take it say why (offline, an agent too old to copy volumes, or one that would close its exposed port or refuse clients without TLS it accepts now). No service moves while one of its backups or restores runs, Back up now and Restore wait while it moves, and a schedule that comes due during a move runs once it ends, on the new node. While a service or database moves, its header says "Moving to <node>..." and Deploy waits; Cancel move asks first and is offered only while cancelling loses nothing (until the data is copied, or until the end for a move without volumes), and puts the service back on the old node with its data. In the API and MCP: `services.moveImpact`.
- **"Use port 6000" when the app listens on another port.** For an app (not a compose member), when the default health check was refused for the whole wait, the agent reads which ports the new container listens on (nothing is needed in the image) and the deploy says so: "The app listens on port 6000, not 80", or, when it listens on the checked port only on 127.0.0.1, that it must listen on 0.0.0.0. The deploy dialog then offers **Use port 6000**: it sets the service's port, moves the domains, the IP:port access and the Cloudflare tunnel that were on the old port, and deploys. With a live version these move when the new version rolls out, and go back if it fails or is cancelled; with nothing live, or the service stopped, they move at once. It is offered on the service's newest deploy only and waits while a deploy runs. In the API and MCP: `services.usePort`. Changing the main port by hand (Advanced tab > Ports, or `services.update`) moves the same things the same way, and the Ports section says what follows the port and when.

## Improved

- **The Overview's Deploys card shows the deploy in progress and the live one.** While a deploy is queued, waiting for a build slot or running, the card shows that deploy with its steps (Queued first while it waits) and how long it has run; under it, one line shows the version that is live now, and a note counts deploys queued behind it. With nothing in progress it shows the newest deploy as before.
- **A failed deploy keeps the app's output apart.** The error is now the reason alone, and the new container's last output is a collapsed, copyable "Last output of the new container" block in the deploy dialog and under the deploy on the Deployments tab, not inside the step log or the red error. Messages from older agents, and deploys that failed before the update, are split the same way when shown.
- **The sidebar and the home page fold projects separately.** Collapsing a project in the sidebar leaves it open on the home page and the other way round, and Expand all / Collapse all only change the home page. Both are saved per person on the panel, so they follow you to other browsers, and the update keeps what you had folded. While projects load, the placeholders take the shape they last had in this browser, so a reload no longer shows every project open first. In the API: `projects.setCollapsed` takes `where` (`sidebar`, the default, or `dashboard`), and projects carry `dashboardCollapsed` next to `collapsed`.
- **Icons on Restart, Stop and Start.** The service header's Restart, Stop and Start buttons have icons (Restart's spins while it runs); Deploy stays text only.
- **Domains that do not exist say so.** A domain typed under a registrable domain that does not exist (not registered, no name servers yet, or a typo) no longer says to add its record "where co.il's DNS is managed": zones now stop at the registrable domain, from the Public Suffix List (co.il, co.uk, com.au, ...), and a delegated sub-zone with its own name servers is still found first. The row says "<domain> does not exist: it is not registered, or has no name servers yet. Check the spelling.", adds "Did you mean ...?" when another domain you can see in the panel is a likely spelling, and still shows the record to create once it exists. Adding such a domain still works and shows the same warning. In the API and MCP: `domains.checkDns` answers `zoneMissing`, `registrable` and `didYouMean`, and `domains.add` / `addAuto` return `warning`.
- **The red count on the Domains tab counts only what needs you.** A Cloudflare-proxied domain the panel has not checked yet, or is still checking, no longer counts; one counts after 30 minutes of checks that did not reach the node. The count's tooltip names the domains, every counted row says why with Check again, and while a proxied domain is being checked its DNS chip says "Checking that requests reach <IP>...".
- **An indexed reference is judged by its item.** The Environment editor's Secret and Public chips judge `${{api.DOMAINS[1]}}` by that one domain, not by the whole list, and agree with what the panel decides on save.
- **A database's timed exposes keep idle connections for 2 hours**, like its exposed port; they were cut after 15 minutes, which broke SQL clients' pooled connections. Needs the node's agent 0.2.16.
- **Changing a service's nodes or moving it while a deploy runs is refused**, naming the deploy to wait for or cancel, because a deploy rolls out on the nodes it started with. Replica counts alone can still change. On the Advanced tab, Save (when the nodes change) and Move wait with the reason on the button.

## Fixed

- **The Overview could show an old deploy after a new one went live.** The Overview's Deploys card could keep the previous deploy (for example "Failed, 1 hour ago") while the console above it already showed the new generation, until the page was reloaded. Every update to a deploy marked every cached deploy list as fresh, the Overview's too, so coming back to it did not fetch again; an update now touches only the lists that hold that deploy. It now fetches whenever it is out of date, checks every minute while nothing is deploying, and again when the tab is shown.
- **Live updates stopped after a laptop slept or changed networks.** A browser cannot tell a connection that died silently from one that is just quiet, so after a Mac slept, changed Wi-Fi, or a proxy lost the connection, a panel tab could stop hearing about changes for good, with no error. The panel now sends a heartbeat every 15 seconds; a tab that hears nothing for about 40 seconds, or gets no answer within 10 seconds of being shown again or of the network coming back, reconnects and reloads what it shows. The panel also closes connections that stayed silent for 150 seconds or fell more than 16 MB behind, instead of dropping their updates unseen.
- **A deploy that ended while its tab was hidden stayed "Building".** The Deployments tab and the header's Deploying / Cancel deploy check again as soon as the tab is shown, instead of up to 15 seconds later.
- **Deploy clocks count with the panel's time.** A running deploy's elapsed time no longer adds the error of a computer clock that is off, and it stops as soon as the deploy has ended.
- **A deploy could wait forever after its service moved to another node.** A rollout on a node that no longer runs the service now fails at once, saying so, and a node that reports no progress for the health timeout plus 5 minutes fails the rollout with "No progress from <node> for N minutes" (plus "<node> is offline" when it is).
- **Back up now on a schedule started it twice while its backup was running.** It is refused now, and the schedule's menu says it is still backing up. In the API and MCP: `backups.runNow` with a `policyId` returns CONFLICT `running` with the run's id.
- **"+1 hour" on a timed expose shortened it** when more than an hour was left: it set the end to one hour from now. It now adds an hour to the time left, and an expose that ended leaves the screen without a reload.
- **Cancelling a move with data let the copy run on.** Cancelling a move while its volumes were copied ended the move but the copy kept going, and a late copy error could turn the cancelled move into a failed one. The copy now stops first, and the service starts again on the old node with its data. Once the data is copied and the service is starting on the new node, cancelling is refused (`deployments.cancel`: CONFLICT `moveStarting`); the move ends on its own there, or back on the old node if it fails. In the API, deployments carry `move` (`from`, `to`, `copying`, `canCancel`).
- **Table headers shifted as times counted up.** On People, API keys and MCP tokens, the Last sign-in, Last used and Expires columns now keep one width, so the header no longer moves when rows load or as "3 minutes ago" becomes "12 minutes ago".
- **A crash loop could raise more than one alert.** A restarted copy that passed its health check before it crashed again (an app with no port and no health check of its own always passes the default check) resolved the streak's crash alert, and the next crash raised another, with a notification. A crash that continues a streak now opens its alert again without notifying anyone, and a deploy result or health report from before the latest crash that arrives late no longer resolves it, also for loops longer than the 200 crashes the panel keeps.
- **On a touch screen, a swipe that began dragging a card and turned into a scroll could leave links dead** until a reload.
- **A proxied domain could stay "needs setup" for good.** Overlapping checks of one domain stored whichever finished last, so an old answer from before the node served the route could replace the newer proof that requests reach it; and when the certificate arrived, the panel cleared that answer but never checked again. Older answers no longer replace newer ones, and the panel keeps checking a domain's origin until it knows it (every 2 minutes in the first hour, 15 minutes in the first day, then every 6 hours), also once it is live.
- **A moved service's IP:port access stayed on the old node.** After a move, a database's exposed port, its timed exposes and a service's first-run IP:port access kept pointing at the old node and stopped working. They now move with the service, on the same port unless another service has it there; services moved by older versions are fixed when the panel starts.
- **Two timed exposes of the same port opened in the same second could swap ports.** Each port now carries its expose's id (older agents: matched by their end time to the millisecond).
- **A Postgres's timed exposes asked for TLS a few seconds early.** Turning on the exposed connection switched their URL and command to `sslmode=require` before TLS was on inside the database; the card now follows what the node reports.

## After the update

- The panel runs migrations 0021 to 0025 at start (per-view collapse, Use port's pending move, backup contents, plain connections, domain origin checks). Nothing to run by hand.
- Update the panel before the nodes. These need the node's agent 0.2.16: connections without TLS, the "listens on port N" hint and Use port, choosing and seeing what a database backup holds, a timed expose's own port id and a Postgres's TLS state on its timed exposes, and the 2-hour idle time of a database's timed exposes. Everything else needs only the panel.
- Service exports keep a backup schedule's chosen databases, and an imported database exposure starts TLS only.
- A service whose own `.env` sets a variable named `DOMAINS`: other services that reference `${{<it>.DOMAINS}}` now get the built-in list of its domains, the way `${{<it>.DOMAIN}}` always got the built-in. Rename the variable if they need its value.
- Deploys that failed before the update keep the app's output in their stored deploy log lines; the error and the output block are split when shown.
