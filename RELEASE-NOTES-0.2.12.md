# Seylo 0.2.12

Update from Settings > Updates: the panel updates first, then each node. Nothing to run on the servers. New installs: `curl -fsSL https://install.seylo.dev | sudo sh`.

What's new in full: https://docs.seylo.dev/self-hosting/whats-new-in-0-2-12

## New

- **Point a joined node at the panel's IP: `seylo set-panel`.** A node that joined over the panel's domain went offline when its network began decrypting HTTPS (a firewall doing TLS inspection, such as a FortiGate, re-signs the domain's certificate, and the agent refuses it), and getting it back meant editing `/var/lib/seylo/config.yml` by hand or joining again with a new token. On the node, `sudo seylo set-panel 'https://<panel IP>:<agents' port>' --pin 'sha256:<key>'` now does it: it first connects to that address and checks that it is the panel this node belongs to (the panel identity the node recorded when it joined, the same check as on every connect), and only then writes `panel_url` and `panel_pin` to config.yml, keeps the previous file as `config.yml.bak`, restarts the agent and prints whether it connected. Another panel, a wrong pin or an address that does not answer changes nothing and says so. The check leaves what the panel knows about the node (its addresses and machine details) as it was. The node keeps its id, its services and every other setting in config.yml, and needs no join token. Without `--pin` the address's certificate must come from a CA the server trusts; plain `http://` to another server needs `--insecure`, as for `join`. Nodes > Add node shows the command, filled in with the panel's IP address, agents' port and pin, under the join command over the panel's IP ("Already joined? Point it here"), and the agent's error for a certificate from an issuer it does not trust names it. The node needs agent 0.2.12: a node that went offline before it updated still needs the hand edit (`panel_url: https://<panel IP>:<agents' port>` and `panel_pin: sha256:<key>`, then `sudo seylo restart`). In the API: `nodes.createJoinToken` returns `setPanelCommand`.
- **A Users tab on databases.** PostgreSQL, MySQL, MariaDB, MongoDB and ClickHouse databases have a Users tab next to Connection that lists the users that can sign in, read from the database itself, with the main user first: the one Seylo signs in with for the shell, the web UI, backups and the connection URLs. Each user shows what it may do (Read only, Read and write, Admin of the database, Full admin, or Custom with its grants), and the tab says why when something cannot be done with one. From there you can make a user with one of those access levels (MySQL and MariaDB also take the host it may sign in from), set a new password you choose or generate one, rename a user, delete one, and use another user as the main one. Passwords of other users show once, with that user's connection URLs, and Seylo does not keep them; it keeps only the main user's, as before. Deleting a user keeps the data: a PostgreSQL user that owns tables gives them to the main user first, once it can no longer sign in and its sessions have ended, so nothing it makes meanwhile is lost; MySQL warns about views, routines, triggers and events that run as the user. Renames keep a user's rights and, on PostgreSQL, its tables; MongoDB has no rename, so a new user with the same rights and a new password takes its place.
- **Change the main user's password and name.** The Connection tab has a Change link next to the user and the password, which opens the Users tab with that change. The main user's password replaces Reset password, with the same type-the-name step. Its name changes where the engine allows it: PostgreSQL renames it in place, also the first user the image made, and restarts the database so its health check uses the new name (you can leave the restart for later); MySQL and MariaDB rename an admin other than root in place; ClickHouse restarts with the new name. MySQL's root and MongoDB's main user stay, and "Use another user as the main one" makes a new user with full rights (or gives an existing one a new password, and full rights only after that worked; a locked user cannot be picked) instead, signs in as it to make sure it works before anything is saved, and can remove the old one (for MySQL's root only root@%, since the image and Seylo's own steps need root inside the container), asking first when views, routines, triggers or events run as it. If the node stops answering in the middle of a change to the main user, Seylo signs in with the new name or password and saves it only when that works. After any change to the main user Seylo lists the services that use the database's name, password or URLs, with a Redeploy link each: they get the new values on their next deploy. Redis, Valkey, KeyDB and Dragonfly have one user, default, and the tab says why only its password changes there.
- In the API and MCP: `databases.users`, `databases.createUser`, `databases.setUserPassword`, `databases.renameUser`, `databases.deleteUser` and `databases.switchMainUser`, all with the `databases.credentials` permission. The four that change or remove a user need a person's approval when a model calls them. `databases.resetPassword` still works and returns `deploymentId` when the database restarts.
- **A node check for the DNS servers Docker gives containers.** Container DNS, on a node's Health tab and in `seylo health`, checks that Docker gives containers DNS servers they can use. A Pelican/Wings node failed every build with "lookup registry-1.docker.io on [::1]:53 ... connection refused" while the server's own DNS worked: its /etc/docker/daemon.json had `"dns"` entries that were not addresses (empty ones), Docker started anyway and gave every container `nameserver invalid IP`, so the build worker could not pull images and apps could not look up outside names. The check runs a short test container from an image already on the node (it never pulls one), reads the running build workers' DNS servers and Docker's `dns` setting (daemon.json and dockerd's `--dns`), and says which entries are wrong and where they are. Its fix: IP addresses (`"dns": ["1.1.1.1", "8.8.4.4"]`) or no `dns` key so containers get the host's servers, `dockerd --validate --config-file /etc/docker/daemon.json`, then `systemctl restart docker`, with a warning that the restart stops every container on the server, Wings' game servers included, unless live-restore is on, and the commands that give build workers still running the new servers (`docker restart`, or `docker buildx rm` and the next build makes a new one). Seylo never changes Docker's settings or restarts Docker itself.

## Improved

- **A clone keeps Deploy on push.** Cloning an app built from a repository (GitHub, a git URL, GitLab, Gitea or Bitbucket) used to turn Deploy on push off on the clone. It now keeps the source's setting, and the Clone dialog has a "Deploy on push" switch that starts as the source's, with a note that each push to the branch then deploys both services. A clone that deploys on push picks up the next push to its branch: through the GitHub App like the source, and for a repository read through the connected GitHub account or a GitLab, Gitea or Bitbucket connection through a repository webhook of its own, created with the clone (polled every minute while the webhook cannot be created, as for any other service). A push that arrives while the clone's data is still being copied waits for the copy: once it is done, the clone deploys the head of its branch, and the webhook's delivery log says so (a copy that failed deploys nothing). A git URL deploys on push through a deploy trigger URL, which a clone does not copy: make one on the clone's Source tab. Export and import are unchanged: an imported service still arrives with Deploy on push off unless you turn it on in the import. In the API and MCP: `services.clone` takes `deployOnPush`; left out, the clone keeps the source's setting.
- **References show a database's internal address on other nodes too.** On the Environment tab, the References panel used to leave out `INTERNAL_URL` and `INTERNAL_HOST` of an exposed database (or an app with a domain) running on another node than the service you edit, so they looked missing. They are listed again, struck through like those of services with no way in, and their tip says which variable to use instead, for example "Only for services on il-ra. api runs on empire, so use EXPOSED_URL." The project network does not reach across nodes, so the exposed URL is still the one that connects.
- **Tested on the real images.** Every step of the Users tab ran on PostgreSQL 18, MySQL 8.4, MariaDB 11.8, MongoDB 9.0 and ClickHouse 26.8 in Seylo's test setup: users of each access level proved what they may and may not do with the database's own client, new passwords, renames and deletes, the main user's password twice before a deploy, its new name in place, by a switch or with a restart, and then the shell, a backup and its restore signed in as the new main user.
- **A build that fails on a name lookup says where to look.** After "The build failed - the lines above say why", a build whose output shows a failed DNS lookup (BuildKit's "lookup ... on ...:53", "dial tcp: lookup" or "no such host", or apt, curl, pip and npm in a RUN step) gets one more line pointing at the node's Container DNS check, so the reason does not hide in BuildKit's output.

## Fixed

- A second password reset of a MongoDB database before its next deploy failed ("the database refused"): the reset signed in with the password the database first started with. It now signs in with the one Seylo stores. PostgreSQL resets also sign in as the stored user, and send the new password to PostgreSQL only as its SCRAM hash, so a failed statement in the database's log shows no password.
- A new password for ClickHouse or Dragonfly was saved but the database kept the old one until something else redeployed it, so the shell, the web UI, backups and services using the new URL could not sign in. Redis, Valkey and KeyDB took the new password at once but went back to the old one on their next restart. These now restart with the new password right after the change, which needs the permission to deploy the database. A stopped database has to be started first, since that restart would start it.
- Restoring a PostgreSQL backup that names a user the database no longer has (renamed or deleted) stopped part way, after the tables it replaces had been dropped. A restore now runs in one transaction: it fails with nothing changed, and its error names the user. Make a user with that name on the Users tab and restore again.
