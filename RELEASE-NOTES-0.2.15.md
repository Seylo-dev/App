# Seylo 0.2.15

Update from Settings > Updates: the panel updates first, then each node. Nothing to run on the servers. New installs: `curl -fsSL https://install.seylo.dev | sudo sh`.

What's new in full: https://docs.seylo.dev/self-hosting/whats-new-in-0-2-15

## New

- **Panel address, per node.** A node's Settings has a Panel address choice: **Follow the panel's domain** (the default, as before: the node moves to the panel's domain once it is live) or **Stay on this address**, which keeps the node on the address it connects to now, usually the panel's IP and pin, and the panel never names its domain to it. It is for a server whose network decrypts HTTPS (a firewall doing TLS inspection re-signs the domain's certificate, and the agent refuses it), where moving to the domain only cuts the node off. `sudo seylo set-panel` on the node now sets Stay by itself, also when config.yml already points at that address (edited by hand), and so does a join with `--pin` at the panel's IP address while the panel has a domain (the Add node dialog's second command; the request goes with the join only, so a node that joined a panel before 0.2.14 that way follows the domain added later). While a node has an open "could not move to the panel address" alert because its network re-signed the domain's certificate, the panel keeps it on Stay until you choose; Settings says why. Choosing Follow on a connected node reconnects it so it moves at once. The panel's own node has no choice: it reaches the panel on its own server. In the API and MCP: `nodes.updateSettings` takes `panelAddressChoice` (`follow` or `stay`, audited), and `nodes.get` returns `panelAddressChoice`, `panelAddressChoiceBy` (`owner`, `node`, `join`, `inspectedCertificate` or `default`) and `panelAddressChoiceAt`. Needs agent 0.2.14 for `set-panel` and the join to ask for Stay; the setting itself works for every node.
- **Why a node is offline.** An offline node's row under Nodes says why when the panel knows: the connect it refused since the node was last seen ("Refused 4 min ago: This agent (0.2.1) is too old for this panel...", or a signature that does not match the node's key), else when it was last seen. Once a node is back, its agent tells the panel the last connect error it had while away, which the panel could not see (a certificate it refused, a name it could not look up, a connection that timed out), and the node's page shows it for a week: "Was offline from 17:39 to 17:46: dial panel: x509: certificate signed by unknown authority ...". The agent keeps that error across a restart while it is away. In the API: `nodes.list` and `nodes.get` have `rejectedHello` for an offline node, and `nodes.get` has `lastOffline` (`from`, `to`, `reason`, `failedAttempts`). The report comes from nodes on 0.2.14.
- **Set one variable through the API and MCP: `env.setVariable`.** An AI working through the MCP server could not fix one line of a service's environment: `env.get` hides every value from models, and `env.set` replaces the whole file, so changing one line meant wiping the values it could not see. `env.setVariable` takes a service, a key and a value and changes only that line. The last line with the key (the one that wins) gets the new value and keeps its quotes when the value fits them, its `export`, its comment and the comment lines above it, `# @public` included. A new key goes at the end, and a `null` value removes the key (every line with it, and a `# @public` or `# @secret` line right above). The value can hold references and goes through the same checks as a save from the editor: a reference to something the caller may not read is refused, as before, but only for the line being written. A value with spaces or a line break is written in double quotes. The activity log shows the key, never the value. A change that would make the file longer than 256 KiB is refused, so the Environment page always loads. `env.setSharedVariable` does the same for a project's shared variables. Both run right away for MCP tokens that may make changes, like `env.set`, and `env.get` and `env.set` now point models to them.
- **Download a backup.** A backup's menu on the Backups tab has Download. The browser saves the file straight from the bucket, so nothing passes through the panel and the bucket needs no CORS settings. The file is named after the service, what it holds and when it started, for example `vault-warden-data-2026-11-13_0300.tar.gz`. The link the panel signs is for that one file and works for 5 minutes, and the bucket's keys are never in it. It needs the restore permission, and on a database also the permission to see its credentials, since a dump holds its logins. Each download is in the activity log. Deleted backups and backups whose destination was deleted have no Download. In the API and MCP: `backups.downloadUrl`; an AI or an MCP token waits for a person's approval first, like a delete, unless Ask before destructive actions is off.

## Improved

- **References list the service's own URL, DOMAIN and internal address.** On the Environment tab, the References panel listed every other service of the project and the shared variables, but not the service you edit, so its own website domain could not be inserted from there. It now starts with that service, marked "this service", and its own built-in variables: `URL`, `DOMAIN`, `INTERNAL_URL`, `INTERNAL_HOST` and `INTERNAL_PORT` for an app, the connection set (`INTERNAL_URL`, `EXPOSED_URL`, `USER`, `PASSWORD`, ...) for a database. A click inserts `${{<its name>.DOMAIN}}` like any other reference, the tip shows the value, and a variable with no value yet (such as `DOMAIN` before the service has a domain) gets no chip until it has one. Its own variables are not listed: a reference to another line of the same file is refused (it could loop back on itself), so write that value instead.
- **`seylo status` names the node as the panel does.** It printed the server's hostname (or the name given when it joined), so a node renamed in the panel showed under another name on the server and read like a different machine. Once the agent has connected it shows the panel's name, a rename made while it is connected included, also after a restart while the panel is away; before the first connect it is the hostname, as before.
- **A failed move is remembered across restarts.** A node whose move to the panel's domain failed because the domain's certificate came from an issuer it does not trust, or did not match the pin, waited 24 hours before trying again, but only in memory: every agent restart, an update included, tried the move once more, dropped the first session the panel accepted and raised the same alert again. The wait is now kept on the node (`/var/lib/seylo/state/panel.json`) and ends when the panel stops naming that address or names another, or when the move works. `sudo seylo set-panel '<url>'` moves the node by hand, for example after adding a CA to the server's trust store.
- **Wider deploy details.** The dialog with a deploy's steps and log (Deployments > Logs) is up to 1280px wide instead of 960px, so build output lines fit without scrolling sideways; the layout is the same. On a phone it takes the screen less 16px a side, and the step cards wrap.
- **The Environment tab says which variables are secrets.** A Secret chip follows each variable that builds and crash reports treat as a secret, and a Public chip follows one whose name or value looks secret but is public (a framework public prefix, or a `# @public` comment). Hovering the chip or the name says why (its name, its value, a reference to another secret, a comment, the prefix), what it changes (a Dockerfile or Railpack build gets a secret only as a build secret, `RUN --mount=type=secret,id=NAME`, not as `ARG NAME`; Nixpacks does not get it; crash reports and troubleshoot uploads hide its value) and which comment changes it. Values of framework-public and `# @public` variables are no longer shown as dots; a `# @secret` one is. In the API and MCP: `env.references` says `secret` for every variable of other services and every shared variable.
- **Hardcoded service URLs get a "use the reference" fix.** A value that spells out another service's address, such as `NEXT_PUBLIC_API=https://api.example.com/v1` while `api.example.com` is the api service's domain, gets a blue hint in the Environment editor with a quick fix to `${{api.URL}}/v1`: the same value, and it follows the domain when it changes. It covers a service's `URL`, `INTERNAL_URL` and `EXPOSED_URL`, a URL followed by a path or query, the service's own address (`${{web.URL}}` for `NEXTAUTH_URL`), and a bare `DOMAIN` or `INTERNAL_HOST` in a variable named for a host or a domain (`API_HOST`, `COOKIE_DOMAIN`, `ALLOWED_HOSTS`). A database's `EXPOSED_HOST` on its own is left alone, since it is often just the node's address. Browser variables (`NEXT_PUBLIC_`, `VITE_`, `PUBLIC_`, `REACT_APP_`, `NUXT_PUBLIC_`, `EXPO_PUBLIC_`, `GATSBY_`, `VUE_APP_`) end up in code that runs in the visitor's browser, which cannot reach the project network, so `INTERNAL_URL` never works in them: for these the fix uses the public URL, also when the value was the internal address, and the hint says that a server-side variable can use `INTERNAL_URL` instead when both services share a node. When the service has no public address yet, the hint says the browser cannot reach it and has no fix. Addresses many services share (`localhost`, an IP address), mail domains, and plain words that happen to be a service's name are left alone. The hint is not counted as a problem and does not block saving. In the API and MCP: `env.set`, `env.analyze` and `env.setVariable` return it as the diagnostic `hardcoded-reference` (severity `info`) with its fix. It names the key and the reference, never the value, so an AI can apply it with `env.setVariable` without seeing the value. A database URL with its password only gets the hint for people who may see the database's credentials, in the editor and in the API.
- **The repository picker starts on the service's repository.** On the Source tab of a service connected to a GitHub repository (through the GitHub App or the connected GitHub account) or a GitLab, Gitea/Forgejo or Bitbucket one, the repository search box now opens with its owner/repo, and the list shows that repository selected and scrolled into view inside the list, with the branch as it is. A repository the list's first page does not show (an organization's, or one pushed to less recently than the others) shows first. Opening the tab searches nothing and changes nothing: the list stays whole and the form says Connected until you pick something else. Clicking or tabbing into the box selects its text, so the first key starts a new search. New services and services with another kind of source start with an empty box, as before.
- **Apps run with `NODE_ENV=production` unless their environment says otherwise.** Every app, whether built from a repository, a Dockerfile or an upload, run from an image, a compose stack member or a pull request preview, now gets `NODE_ENV=production` in its container, the way apps built from a repository get `PORT`. A `NODE_ENV` in the app's `.env` (for a compose member, its `environment:` block) or in the project's shared variables wins, whatever its value, also an empty one. Builds do not get it, so `npm ci` in a Dockerfile still installs devDependencies; a `NODE_ENV` you set reaches the build as before. It also replaces a `NODE_ENV` the image sets itself (`ENV NODE_ENV=...`). Databases, Boxes and cron jobs get none. Apps that are running get it on their next deploy, not on a restart, which keeps the environment the app was deployed with. If an app must run with another value, set `NODE_ENV` in its `.env` before you deploy it.
- **Builds at once has an Auto setting.** A node's Settings > Builds at once is now Auto or a fixed number from 1 to 16. Auto is sized from the node's cores and memory: one build per 4 cores and per 4 GB of memory, whichever allows fewer, at least 1 and at most 16 (a node with 28 cores and 157 GB runs 7, one with 32 cores and 121 GB runs 8, one with 4 cores and 8 GB runs 1). The field shows what Auto runs on the node now, for example "Auto - 7 now", and it follows the machine: a node that comes back on other hardware gets the new number. New nodes start on Auto; existing nodes keep their number until you pick Auto. Nodes need no update for it. In the API and MCP: `nodes.list` and `nodes.get` have `parallelBuildsAuto`, with `maxParallelBuilds` the number that applies now; `nodes.updateSettings` takes `parallelBuildsAuto` (true for Auto, false to keep the number that applies now as a fixed one), and `maxParallelBuilds` alone still sets a fixed number and turns Auto off.
- **Deploys wait for the image's own HEALTHCHECK.** An app or compose member with no health check of its own used to get TCP on its first port, which passes as soon as the app listens: a web image went healthy 1.2 seconds after it started, before it could serve, and an api whose boot migrations wait on a lock got traffic before they ran. Now, when the image declares a HEALTHCHECK, the deploy switches traffic only once Docker calls the new container healthy, and fails as soon as Docker calls it unhealthy, with the check's last output in the deploy error; the old version keeps serving. Docker runs the image's own command with its interval, timeout, start period and retries (Seylo reads the result, it never runs the command), and after the deploy the health state, alerts and load balancing follow it too. Images without a HEALTHCHECK (or with `HEALTHCHECK NONE`) keep TCP on the first port, and a check you set (TCP, HTTP or a command) still replaces it. The deploy waits long enough for the image's start period: at the default health timeout (300 seconds) it waits at least the start period plus retries times interval and timeout, plus a minute, so an image with a 600 second start period gets about 12 minutes; a health timeout you set is used as set, and the deploy log says when it is shorter than the image's start period. The health check card on the Advanced tab says what applies ("Image HEALTHCHECK: <command>, every 10s, start period 600s, 3 retries", or "TCP on port 3000"). It applies from each service's next deploy, on nodes with agent 0.2.14 (older nodes keep the TCP check); databases, Boxes, cron services and compose members whose file turns health checks off (`healthcheck: disable: true`) are unchanged, and nothing running is restarted by the update. In the API and MCP: `services.get` returns `imageHealthCheck`.
- **Containers run with an init process (Tini) by default, like Easypanel.** Apps, compose members and cron jobs ran their program as PID 1, where Linux ignores signals it has no handler for and nothing reaps the zombie processes it leaves behind, so an app started through a wrapper could miss the stop signal and be killed when the stop timeout ran out. Now their containers run Docker's init (`docker run --init`: Tini as PID 1), which passes SIGTERM and the other signals on to the app and reaps zombies. A new setting on the Advanced tab, Container > Init process, picks Auto (the default), On or Off. Auto is on, except for images that run their own init as PID 1 and must stay PID 1: when the main program (the entrypoint, the service's or the image's, or without one the command) is `/init` (s6-overlay, as in linuxserver.io images), another `init` or systemd, tini, dumb-init, docker-init, catatonit or an s6 program, it stays off. On runs Tini in front of those too; Off runs none. A compose member takes the file's `init:` (true or false) when it sets one, else Auto. It applies from each service's next deploy, which makes new containers; the update restarts nothing, and nodes before agent 0.2.14 run without an init until they update and the service deploys again. Databases, Boxes and the panel run as before. In the API and MCP: `services.update` takes `container.init` (`auto`, `on` or `off`), and `services.get` returns it.
- **A new Traefik image no longer adds its download to the downtime.** When a node replaces its Traefik (an update that changes its image or settings), it now pulls the new image while the old Traefik still serves, and only then swaps them. Sites on the node are down only for the swap itself, about half a second in Seylo's test setup.
- **A deploy whose container never listens on its port says so, and what to do for a background worker.** New app services get port 80, and without a health check of their own a deploy waits for TCP on that port. A background worker (a Dockerfile app with no domain that never serves on a port) failed after the whole 5 minute health timeout with only "not healthy after 5m0s: health check never passed: tcp check on port 80: dial tcp 172.29.0.9:80: connect: connection refused". When that check was refused on every try, the error now goes on: "Nothing in the container listens on port 80. If this service does not serve on a port (a background worker), remove the port under Ports in the Container section of the service's Advanced tab (no domain uses it), or set a check that fits it under Health check and deploys on the same tab. If it does serve, it must listen on port 80 on all addresses (0.0.0.0), not only on 127.0.0.1." A compose member is pointed at its stack's compose file instead, and a service whose domains use the port is told the app must listen there. A check that timed out, an HTTP or command check, or a TCP check you set keep the plain error, and nothing about the defaults or the check changed: the deploy still fails until the port goes or a fitting check is set. On nodes with agent 0.2.14.
- **References list only variables that have a value.** On the Environment tab, a variable that is empty right now gets no chip: `URL` and `DOMAIN` of a service without a domain (the service itself included), a database's `EXPOSED_*` while it is not exposed, and an empty shared variable. A service or the shared variables with nothing left are not listed. A value you may not see, such as another service's variables or a database password without access to its credentials, keeps its chip. A reference typed by hand, such as `${{web.DOMAIN}}`, still works and gets its value once the service has a domain.
- **References the app would get as text get a warning.** In the Environment editor, `${{api.URL}}` inside single quotes (which keep it as text) and `api.DOMAIN` written without `${{ }}` now get an amber warning with a quick fix: **Use double quotes**, or **Use `${{api.DOMAIN}}`**. For a name that is no service, such as `blabla.DOMAIN`, there is no wrap fix, only the closest service names when one is a typo away. A token counts only when its variable part is an exact variable name in capitals, so `example.com`, `api.domain`, `api.DOMAIN.com` and `https://api.DOMAIN` are left alone. Saving is never blocked, and the Shared variables sheet, which takes no references, shows neither. In the API and MCP, `env.set`, `env.analyze` and `env.setVariable` return them as `single-quoted-reference` and `bare-reference` (severity `warning`) with their fixes; they name the key, the token and the reference, never the rest of the value.
- **The console reconnects by itself.** The Console tab and the Overview's console card used to follow a restart for two minutes only; any other break (a network drop, the agent reconnecting, a panel restart, an app started later) left them at "Disconnected. Reconnect" while the app ran. Now, while the app runs or is starting, the console connects again by itself, after 1 second and backing off to 8 seconds. While nothing runs it says "The app is not running. Its console connects when it starts." and connects as soon as the app starts or a deploy goes live, with no click. Opening the page, coming back to the browser tab and the network coming back also reconnect it, and the Overview shows the console while the app is still starting. It stops at Reconnect, with the reason, when the panel refuses it (no permission, the service gone, an agent too old), after about 25 seconds of tries that cannot attach (for example when the service's first node is offline), or after the 30-minute idle timeout, which now says so. A shell still never reopens by itself.
- **A shorter, wider References panel.** On the Environment tab, the References panel grew with its chips, so a service with 30 variables of its own made a long column next to the editor. It now stops at the editor's height and its list scrolls inside it, with no scrollbar (the edge that hides more fades out), by mouse wheel, keys or Tab; the title and hint stay at the top. Each group (the service you edit, every other service, the shared variables) collapses and expands with a click on its header row, or Enter or Space. A group with more than 12 variables starts collapsed and shows how many it holds ("34 variables"), the others start expanded, and Expand all / Collapse all in the header does every group. What you expand or collapse is remembered in this browser for each project. The panel is also wider: up to 440px instead of about 320px, while the editor keeps at least 600px next to it; on a narrow screen it still goes under the editor.
- **Back up now backs up every schedule.** On a service's Backups tab, Back up now ran only the first schedule, so a service with a schedule per volume got one backup. It now starts every schedule that is on at once; each backup goes to its own destination and counts toward its own Keep newest, and the toast says how many started. Schedules that are off, and one whose backup is still running, are skipped. Back up now on a database's Connection tab does the same; a database without a schedule still gets a one-off dump to the first destination, and each schedule's own menu still backs up just that schedule. In the API and MCP: `backups.runAll`.
- **Backups say what they hold.** Each row of Backups and restores names what it backed up next to its date: "Database", "Volume data", and for a restore "Restore of the Nov 12 03:00 backup of Volume data". In the API and MCP, runs have `volumeName`, and restores `sourceStartedAt`.

## Fixed

- A watch path like `apps/docs/..` was saved and then skipped every push. Patterns start at the repository root and git names changed files without `.` or `..` segments, so such a pattern (`apps/docs/..`, `../shared/**`, `src/./lib`) never matches a file, and every push after it was "Skipped by watch paths". Saving now refuses it with a hint, for example "apps/docs/.. never matches a file: paths start at the repository root. To watch a folder, write apps/docs/**". The Watch paths card shows the same message under the patterns as you type and keeps Save off until it is fixed; `services.setWatchPaths` in the API and MCP refuses it with the entry's field (`watchPaths.<n>`), and an import leaves such watch paths out with a warning. Patterns stay what they were: `*` (not across `/`), `**` (across folders), `?` and `!` to exclude, and a leading `./` is still dropped. Patterns saved before are not changed: if the Source tab shows the message for one, replace it with the pattern it suggests, or its pushes keep being skipped.
- A node next to Wings stayed offline for about 7 minutes after the panel restarted for its update, though its config.yml had a working fallback: it had moved to the panel's domain earlier, and once its network began re-signing the domain's certificate (TLS inspection, here a FortiGate in front of a domain behind Cloudflare's proxy) every connect there failed on "x509: certificate signed by unknown authority", while the agent tried the fallback (the panel's IP and pin) only after 5 minutes of failures, then the owner put the IP and pin back by hand. A connect that fails on a certificate the node will never trust (an issuer it does not trust, or a key that is not the pinned one) now goes to the fallback on the next attempt, and the agent does not dial the domain again from there when the panel names it: it makes the IP and pin its address again and raises one alert, which keeps the node on Stay. A timeout or a refused connection still waits the 5 minutes, so a short panel restart does not move a node off its address, and so does Traefik's own default certificate: the panel's server answers with it while it has no certificate for the name (its proxy just restarted, a certificate is being issued again), which passes on its own and does not put the node on Stay.
- A `NEXT_PUBLIC_..._KEY` variable never reached a Dockerfile build. A Next.js app whose Dockerfile checks `ARG NEXT_PUBLIC_TURNSTILE_SITE_KEY` failed with "NEXT_PUBLIC_TURNSTILE_SITE_KEY: is a required build arg", while `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_WEB_URL` arrived: the name has KEY in it and the value looks like a token, so Seylo took it for a secret, and a Dockerfile build gets secret variables only as BuildKit secret files, never as build args. Variables whose names start with a framework's public prefix are now public, whatever their name or value says, since the framework ships their values to every browser: `NEXT_PUBLIC_` (Next.js), `NUXT_PUBLIC_` (Nuxt), `EXPO_PUBLIC_` (Expo), `REACT_APP_` (Create React App), `VUE_APP_` (Vue CLI), `GATSBY_` (Gatsby), `VITE_` (Vite) and `PUBLIC_` (SvelteKit, Astro). They are Dockerfile build args, Nixpacks builds get them, and crash reports keep their values. `# @secret` on the line above still makes one a secret, and a password stays one under any of these prefixes: a URL with a password (`PUBLIC_DATABASE_URL=postgres://user:pass@...`, as written or after its references resolve) or a reference to a database's `PASSWORD` or connection URL, also through another variable. Its Secret chip says why the prefix did not decide; `# @public` makes it public if the browser should get it. Redeploy the service for its build to get them. Dockerfile builds also say when an ARG of the Dockerfile (any stage) names a secret variable: "NAME is a secret, so the build gets it as a BuildKit secret (RUN --mount=type=secret,id=NAME), not as ARG NAME. If it is not secret, add "# @public" above it in the service's environment." before the build output, and again as the last line when a failed build's output mentions it. The note comes from nodes on 0.2.14.
- Typing fast in a code editor (Environment, Shared variables, Notes, custom CSS and the others) could lose keys: the editor sometimes put back an older text of its own while the page caught up, so what was typed after it was gone. It now keeps every key.
- **Builds waiting for a free slot on their node showed as running; they now show as waiting, with their place in line.** A node runs as many builds at once as its Builds at once setting allows and queues the rest, but the panel marked every build running the moment it sent it to the node: `builds.queue` listed two builds of one project as running on a node that runs one at a time, and the waiting one's deploy said "Fetching source". A build now stays queued until its node really starts it. While it waits, its Clone step reads "Waiting for a build slot on <node> - 2 ahead" (or "next in line"), updated as the builds ahead of it start, finish or are cancelled, and counted in the order the node got the builds, which is the order it starts them in (a build whose archive or source lookup takes longer is behind the ones that reached the node first), and the service header, the deploy list, the build log, the sidebar and the dashboard say "Waiting for a build slot" where they said "Building". The build node picker on the Source tab says how many builds run and how many wait on each node ("1 running, 2 waiting"). "Built in" times count from the build's real start instead of from when it was sent, and the Clone step's time leaves out the wait. A waiting build is no longer failed by the 90-minute build timeout while the builds ahead of it run: it fails when no build started or finished on its node for 90 minutes, or once it has waited 6 hours (the node lost it but goes on with other builds). Cancelling a waiting deploy takes its build out of the node's queue. Works with nodes on 0.2.11 and later. In the API and MCP: `builds.queue` builds are `queued` until their node starts them, `position` is their place among the node's queued builds and the new `waiting` says the node has no free slot for them; `builds.getSettings` nodes have `running` and `waiting`; deployments have `buildWait` (the node and the place in line) and services `buildWaiting`.
- **Apps behind a node that forwards to another node saw that node, not the visitor.** With a service's copies on several nodes, a request that came in on one node and was served by a copy on another reached the app with the forwarding node's address in `X-Forwarded-For` and `X-Real-Ip`, and `X-Forwarded-Proto: https` even when the visitor used plain http. An app that rate limits or logs by the last `X-Forwarded-For` hop saw every visitor through that node as one. The node that serves the copy now keeps the headers the forwarding node set from the visitor's connection, without adding the forwarding node: the app sees the visitor's address as the last `X-Forwarded-For` hop and as `X-Real-Ip`, and the scheme the visitor used. Only another node with a certificate the panel issued to it reaches that entry point, so nobody else can set these headers; what a visitor sends in them is still dropped where it comes in. The node that serves the copy needs 0.2.14 for this; until it updates, it works as before.
- **Visitors over IPv6 reached apps as the address of Docker's bridge.** On a node with a public IPv6 address, a visitor over IPv6 arrived at the app as the bridge's gateway (`172.x.0.1` in `X-Forwarded-For` and `X-Real-Ip`), the same for every IPv6 visitor, because Docker's userland proxy took IPv6 connections to ports 80 and 443 and opened its own to Traefik. The node's Traefik now also joins `seylo-edge6`, an IPv6-only Docker network, so Docker forwards IPv6 visitors to it with their own address, as it does for IPv4. This needs Docker 28 or later; the node does it only when turning on IPv6 forwarding, which an IPv6 Docker network needs, would not stop the server taking its own IPv6 address or route from router advertisements. Where it would, the agent logs which interfaces to set `accept_ra=2` on and leaves IPv6 as it was. Nodes next to Wings serve visitors through Wings' Traefik on Wings' network, which already keeps their address when that network has IPv6 on (Wings' default; checked in Seylo's test setup).
- Updating a node to 0.2.14 replaces its Traefik (or, next to Wings, its LB Traefik) once, for the forwarded headers above: sites on the node drop for about half a second, and open connections (event streams and WebSockets included) are cut once.
- A build worker created while Docker had lost its DNS setting kept failing builds until someone restarted it by hand. A container keeps the DNS servers it started with: on Docker 29.0 to 29.2 a `systemctl reload docker` empties the `dns` setting until Docker restarts (moby#52060), and a project's build worker made in between had no server it could use, so every build there failed to pull images, also after Docker gave new containers servers again. The Container DNS check named the worker and said to run `docker restart` on it. Now the agent restarts it itself and the build cache stays: before a build uses it, with one line in the build log ("The build worker had no DNS server it could use ...; restarted it, which keeps the build cache"), and when the node's Container DNS check finds it, whose result then says it restarted the worker. It never restarts a worker a build runs on, and while Docker still gives new containers no DNS server it restarts nothing and the check's fail and fix stay as before. On nodes with agent 0.2.14.
