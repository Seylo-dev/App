# Seylo 0.2.14

Update from Settings > Updates: the panel updates first, then each node. Nothing to run on the servers. New installs: `curl -fsSL https://install.seylo.dev | sudo sh`.

What's new in full: https://docs.seylo.dev/self-hosting/whats-new-in-0-2-14

## New

- **Panel address, per node.** A node's Settings has a Panel address choice: **Follow the panel's domain** (the default, as before: the node moves to the panel's domain once it is live) or **Stay on this address**, which keeps the node on the address it connects to now, usually the panel's IP and pin, and the panel never names its domain to it. It is for a server whose network decrypts HTTPS (a firewall doing TLS inspection re-signs the domain's certificate, and the agent refuses it), where moving to the domain only cuts the node off. `sudo seylo set-panel` on the node now sets Stay by itself, also when config.yml already points at that address (edited by hand), and so does a join with `--pin` at the panel's IP address while the panel has a domain (the Add node dialog's second command; the request goes with the join only, so a node that joined a panel before 0.2.14 that way follows the domain added later). While a node has an open "could not move to the panel address" alert because its network re-signed the domain's certificate, the panel keeps it on Stay until you choose; Settings says why. Choosing Follow on a connected node reconnects it so it moves at once. The panel's own node has no choice: it reaches the panel on its own server. In the API and MCP: `nodes.updateSettings` takes `panelAddressChoice` (`follow` or `stay`, audited), and `nodes.get` returns `panelAddressChoice`, `panelAddressChoiceBy` (`owner`, `node`, `join`, `inspectedCertificate` or `default`) and `panelAddressChoiceAt`. Needs agent 0.2.14 for `set-panel` and the join to ask for Stay; the setting itself works for every node.
- **Why a node is offline.** An offline node's row under Nodes says why when the panel knows: the connect it refused since the node was last seen ("Refused 4 min ago: This agent (0.2.1) is too old for this panel...", or a signature that does not match the node's key), else when it was last seen. Once a node is back, its agent tells the panel the last connect error it had while away, which the panel could not see (a certificate it refused, a name it could not look up, a connection that timed out), and the node's page shows it for a week: "Was offline from 17:39 to 17:46: dial panel: x509: certificate signed by unknown authority ...". The agent keeps that error across a restart while it is away. In the API: `nodes.list` and `nodes.get` have `rejectedHello` for an offline node, and `nodes.get` has `lastOffline` (`from`, `to`, `reason`, `failedAttempts`). The report comes from nodes on 0.2.14.

## Improved

- **References list the service's own URL, DOMAIN and internal address.** On the Environment tab, the References panel listed every other service of the project and the shared variables, but not the service you edit, so its own website domain could not be inserted from there. It now starts with that service, marked "this service", and its own built-in variables: `URL`, `DOMAIN`, `INTERNAL_URL`, `INTERNAL_HOST` and `INTERNAL_PORT` for an app, the connection set (`INTERNAL_URL`, `EXPOSED_URL`, `USER`, `PASSWORD`, ...) for a database. A click inserts `${{<its name>.DOMAIN}}` like any other reference, the tip shows the value ("Empty for now" for `DOMAIN` before the service has a domain), and the value is filled in when the service deploys. Its own variables are not listed: a reference to another line of the same file is refused (it could loop back on itself), so write that value instead.
- **`seylo status` names the node as the panel does.** It printed the server's hostname (or the name given when it joined), so a node renamed in the panel showed under another name on the server and read like a different machine. Once the agent has connected it shows the panel's name, a rename made while it is connected included, also after a restart while the panel is away; before the first connect it is the hostname, as before.
- **A failed move is remembered across restarts.** A node whose move to the panel's domain failed because the domain's certificate came from an issuer it does not trust, or did not match the pin, waited 24 hours before trying again, but only in memory: every agent restart, an update included, tried the move once more, dropped the first session the panel accepted and raised the same alert again. The wait is now kept on the node (`/var/lib/seylo/state/panel.json`) and ends when the panel stops naming that address or names another, or when the move works. `sudo seylo set-panel '<url>'` moves the node by hand, for example after adding a CA to the server's trust store.

## Fixed

- A watch path like `apps/docs/..` was saved and then skipped every push. Patterns start at the repository root and git names changed files without `.` or `..` segments, so such a pattern (`apps/docs/..`, `../shared/**`, `src/./lib`) never matches a file, and every push after it was "Skipped by watch paths". Saving now refuses it with a hint, for example "apps/docs/.. never matches a file: paths start at the repository root. To watch a folder, write apps/docs/**". The Watch paths card shows the same message under the patterns as you type and keeps Save off until it is fixed; `services.setWatchPaths` in the API and MCP refuses it with the entry's field (`watchPaths.<n>`), and an import leaves such watch paths out with a warning. Patterns stay what they were: `*` (not across `/`), `**` (across folders), `?` and `!` to exclude, and a leading `./` is still dropped. Patterns saved before are not changed: if the Source tab shows the message for one, replace it with the pattern it suggests, or its pushes keep being skipped.
- A node next to Wings stayed offline for about 7 minutes after the panel restarted for its update, though its config.yml had a working fallback: it had moved to the panel's domain earlier, and once its network began re-signing the domain's certificate (TLS inspection, here a FortiGate in front of a domain behind Cloudflare's proxy) every connect there failed on "x509: certificate signed by unknown authority", while the agent tried the fallback (the panel's IP and pin) only after 5 minutes of failures, then the owner put the IP and pin back by hand. A connect that fails on a certificate the node will never trust (an issuer it does not trust, or a key that is not the pinned one) now goes to the fallback on the next attempt, and the agent does not dial the domain again from there when the panel names it: it makes the IP and pin its address again and raises one alert, which keeps the node on Stay. A timeout or a refused connection still waits the 5 minutes, so a short panel restart does not move a node off its address, and so does Traefik's own default certificate: the panel's server answers with it while it has no certificate for the name (its proxy just restarted, a certificate is being issued again), which passes on its own and does not put the node on Stay.
